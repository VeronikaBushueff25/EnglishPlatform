# Решения по архитектуре

Короткий журнал решений, принятых по ходу этапов. План и ТЗ лежат в docx рядом с исходным ТЗ.

## 1. Фоновые задачи: Hangfire + Hangfire.PostgreSql (этап 1)

План требует выбрать Hangfire или Quartz.NET и хранить очередь в PostgreSQL, чтобы задачи
не дублировались между экземплярами api. Выбран Hangfire:

- хранилище в PostgreSQL ставится одним пакетом, схема создаётся автоматически;
- нужные задачи простые (отправка письма, пересчёт агрегатов, чистка токенов),
  сложное расписание Quartz не требуется;
- встроенная панель удобна для отладки.

Подключается в модуле, которому задачи нужны первыми (письма сброса пароля, этап 2).

## 2. Валидация запросов: DataAnnotations + фильтр эндпоинта

Встроенная валидация minimal API в .NET 10 работает через генератор кода и плохо видит
типы из других сборок, а эндпоинты живут в сборках модулей. Поэтому используется свой
`ValidationFilter<T>` (BuildingBlocks.Infrastructure): атрибуты DataAnnotations на DTO,
ответ 400 в формате ValidationProblemDetails.

## 3. Клиент API для Angular: ng-openapi-gen

OpenAPI-документ пишется при сборке Host в `openapi/openapi.json`. Из него `npm run api:generate`
генерирует сервисы на HttpClient в `web/src/app/core/api`. CI проверяет, что и документ,
и клиент совпадают с закоммиченными.

## 4. Тесты запускаются через Microsoft.Testing.Platform

.NET 10 SDK не запускает xUnit v3 через старый VSTest, поэтому в global.json включён
`"test": { "runner": "Microsoft.Testing.Platform" }`. Команда: `dotnet test --solution EnglishPlatform.slnx`.

## 5. Интеграционные тесты без Docker

Testcontainers требует Docker. Если его нет, можно указать свою базу:
`TEST_DATABASE_CONNECTION="Host=localhost;Database=english_platform_tests;Username=...;Password=..."`.
Без базы интеграционные тесты помечаются пропущенными, а не падают.

## 6. Интерфейс: Tailwind CSS 4 + spartan/ui (этап 2)

Компоненты spartan/ui (аналог shadcn/ui для Angular) не ставятся пакетом: их код генерируется
в `web/libs/ui` и принадлежит проекту, его можно менять. Поведение и доступность берутся из
`@spartan-ng/brain` (на базе Angular CDK), внешний вид — классы Tailwind.

- Почему не Angular Material: узнаваемый вид Google, сложно уйти от него в собственный дизайн
  карточек и занятий. PrimeNG тяжелее и тянет лишнее.
- Стиль `maia` (мягкие скруглённые формы), базовая тема `neutral`, основной цвет — синий.
  Цвета заданы токенами в `web/src/styles.css` (светлая и тёмная тема).
- Тёмная тема включается классом `.dark` на `<html>` по системной настройке
  (скрипт в `index.html`, выполняется до загрузки приложения).
- Новый компонент: `npx ng g @spartan-ng/cli:ui --name=<имя>` в `web/`; настройки генератора в `web/components.json`.
- Иконки: `@ng-icons/lucide`. Уведомления «сохранено»/ошибки: `toast` из `@spartan-ng/brain/sonner`.
- Загрузка данных в экранах — через `resource()` Angular (состояния загрузки и ошибки без ручных флагов).

## 7. Словарь: хранение и наполнение (этап 3)

- **Переводы и примеры — jsonb в `lexemes`, категории — `uuid[]` с GIN-индексом**, а не отдельные таблицы
  `lexeme_translations`/`lexeme_categories` из плана. Они читаются и пишутся только вместе со словом, а фильтр
  по категории — это `category_ids @> …`. Отдельные таблицы понадобятся, если появится поиск по примерам.
- **Поиск** — по денормализованной строке `search_text` (текст и все переводы в нижнем регистре, ё → е).
  Сначала точное совпадение, затем по началу слова, затем остальные.
- **Уникальность** — текст + часть речи (`run` — глагол и существительное — два слова), NULLS NOT DISTINCT.
- **Слово в личном словаре — копия**, а не ссылка (подробности в progress.md, этап 3).
- **Стартовый набор** составлен вручную для проекта — так нет вопроса лицензии. Внешние словари
  (Wiktionary — CC BY-SA, требует указания авторства и той же лицензии для производных) — отдельное решение.
- **Произношение** — синтезатор речи браузера (Web Speech API), если у слова нет ссылки на аудио. Бесплатно,
  работает офлайн, качество зависит от голосов системы.
- В `libs/ui/utils` убран реэкспорт `provideSpartanHlm`: он тянул CDK overlay (~46 КБ) в начальный бандл.

## 8. Повторение: своя реализация FSRS-5, оценка из ответа (этап 4)

- **FSRS написан в проекте** (`SpacedRepetition.Domain/Fsrs.cs`, ~150 строк), а не взят пакетом: готовые .NET-пакеты
  мы не проверяли, а формулы короткие и детерминированные. Корректность закреплена тестами с числами, посчитанными
  отдельно по формулам py-fsrs (FSRS-5, веса по умолчанию). Без «размытия» интервалов — расписание предсказуемо.
- **Две карточки на слово** (узнавание и вспоминание) — как в плане. Вспоминание открывается, когда узнавание
  впервые перешло в Review.
- **Пользователь не ставит оценку сам**: она выводится из ответа и времени. Пороги — в конфигурации, подбираются
  на живых данных.
- **Журналы только дописываются**: `review_logs` и `exercise_attempts` переживают удаление слова и карточки
  (без внешних ключей) — это сырьё для подбора личных весов FSRS и статистики.
- **Занятие хранит очередь и текущее задание в jsonb** своей строки: читаются и пишутся только целиком. Правильные
  ответы остаются на сервере, клиенту уходит задание без них.
- **Три модуля общаются через Contracts**: `IUserWordsReader` (Vocabulary), `IReviewScheduler` (SpacedRepetition),
  `IExerciseEngine` (Exercises), `IUserLearningSettings` (Users). Сохранения в трёх схемах — разными транзакциями;
  повторная отправка ответа с тем же `attemptId` досдвигает занятие, если ответ записался, а занятие — нет.

## 9. Ошибки и адаптация без ИИ (этап 5)

- **Счётчики, а не модель**: как и задумано в плане, анализ повторяющихся ошибок — это счётчики по тегам, форматам и
  словам в `analytics.error_stats`. Они обновляются событием `AnswerChecked` и пересобираемы из журнала попыток.
- **Проблемное слово** определяют два источника: FSRS (сколько раз забыто после выучивания) и Analytics (доля недавних
  неудач). Пороги — в конфигурации.
- **Разминка не трогает расписание**: лёгкий формат перед основным заданием пишется в журнал (оценка 0) и в счётчики,
  но не в FSRS — иначе слово получало бы два ответа за один показ.
- **Правило к ошибке** берётся из справочника типов ошибок (Grammar), тексты тем редактируются в админке без релиза.
- В фронтенде функции API в начальном бандле импортируются по одной (`core/api/fn/...`), а не из общего
  `functions.ts`: иначе каждый новый эндпоинт увеличивает первую загрузку.

## 10. Тест уровня: «лесенка» вместо IRT (этап 6)

- План просил адаптивный тест. Полноценная IRT-модель требует откалиброванных на живых ответах параметров вопросов,
  которых у нас нет. Поэтому — «лесенка»: шаг вверх после верного ответа, вниз после ошибки. Она быстро сходится к уровню
  и проверяема тестами. Когда накопятся ответы, банк можно откалибровать и перейти на IRT, не меняя API.
- Уровень хранится по навыкам (лексика, грамматика, чтение), общий — среднее с округлением вниз: лучше дать чуть проще,
  чем отпугнуть.
- Стартовый набор слов добавляется только после первого теста: повторный тест обновляет уровни, но не засыпает словарь.

## 11. Статистика и выпуск (этап 7)

- **Активный словарь** — слово, которое пользователь вспоминает сам (карточка вспоминания) со стабильностью FSRS ≥ 21 дня:
  через три недели вероятность вспомнить ≥ 90 %. Пассивный — узнаёт (карточка узнавания выучена). Порог в конфигурации.
- **Статистика считается на лету** из журнала ответов (индекс по пользователю и времени), без отдельных агрегатов:
  за год у активного пользователя — десятки тысяч строк, это миллисекунды. Агрегаты по дням — когда упрёмся.
- **Service worker свой, не `@angular/service-worker`**: 60 строк, понятная стратегия, начальный бандл не растёт
  (лимит 500 кБ). Если понадобятся push-уведомления или фоновая синхронизация — перейти на Workbox/ngsw.
- **e2e — Playwright с установленным браузером** (`channel: msedge`), без скачивания браузеров: работает на машине
  разработчика и в CI с Chrome. Нагрузка — свой скрипт на Node без зависимостей вместо k6.
- **Счётчики под конкуренцией — атомарный upsert в SQL**, а не чтение-изменение-запись через EF.
- **Пул соединений ограничен по умолчанию** (30 на экземпляр API), чтобы несколько экземпляров и фоновые задачи
  не упирались в `max_connections` Postgres.

## 12. Тест уровня: модель ответа вместо «лесенки»

- «Лесенка» с правилом «уровень — самый высокий, где было верно» ломалась на угадывании: один удачный ответ на C1
  из одного вопроса давал C1. Теперь оценка θ — среднее апостериорного распределения по модели
  P(верно) = g + (1 − g)·σ(2,5·(θ − уровень вопроса)), g = 1/число вариантов; «Не знаю» — без угадывания.
  Априорно N(2,0; 2,5) — широкое, чтобы C2 тоже находился. Параметры выбраны моделированием (тест и скрипт).
- Это ещё не настоящий IRT: трудность вопроса = его уровень CEFR, а не откалиброванный параметр. Когда накопятся
  ответы, трудности можно откалибровать, не меняя API.

## 13. Словарь: «ядро + по запросу», а не весь словарь в базе

- Полный английский Викисловарь — сотни тысяч статей и гигабайты; ученику нужны ~10 тысяч слов. Поэтому:
  список уровней CEFR встроен (≈180 кБ), статьи берутся из kaikki.org по одной, когда слово впервые ищут
  (или фоновой загрузкой ядра), и сохраняются в общую базу. Ответы, включая «нет такого», кешируются.
- Слова из словаря попадают в базу сразу (иначе их нельзя добавить себе), но с `needs_review`: администратор
  проверяет, правка снимает пометку.
- Источник — Викисловарь (CC BY-SA): указываем источник в интерфейсе; CEFR-J — с цитированием, Octanove — CC BY-SA.

## 14. Оформление и вес начальной загрузки

- Палитры — отдельные CSS-файлы в `public/themes/`, подключаются скриптом в `index.html` до запуска Angular:
  нет вспышки и нет веса в начальной загрузке. Выбор — в localStorage (это настройка устройства).
- Пакет иконок lucide — один модуль: если его импортирует хоть что-то из начальной загрузки, туда попадают все
  иконки всех ленивых страниц. Шапка и уведомления используют свои копии SVG (`core/header-icons.ts`,
  `libs/ui/sonner/.../toaster-icons.ts`) — main сократился на 18 кБ и больше не растёт от новых иконок.
